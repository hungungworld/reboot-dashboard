## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 회사 | **알디콤 (ALDICOM)** — 한국 숙취해소제 기업 |
| 신규 라인 | **Reboot** — 미국 시장을 위한 새로운 라인 |
| 출시 목적 | 미국 소비자에게 낯선 카테고리인 숙취해소제를 더 친숙하게 소개하기 위함 |

| 판매 채널 | Amazon(일반 미국 소비자), Weee · Yamibuy(아시아계), TikTok · Instagram(2030 숏폼) |

| 서비스 형태 | 사내 업무용 웹 대시보드 (Flask) |

### 한 줄 목표

> **"효능을 말할 수 없는 상태에서, 낯선 카테고리를, 여러 채널에, 정확한 타이밍에 알린다."**
> → 규제를 지키면서, 채널별로, 시즌에 맞춰 **빠르게 콘텐츠를 만드는 방법**을 제공한다.

> ※ 공개 자료를 바탕으로 팀이 설정한 가상 인물입니다.

> *"한국에선 '숙취해소력'이 무기인데, 미국에선 그 단어를 못 써요. 그래서 카피 한 줄에 반나절이 걸려요."*

## 3. 해결하려는 문제

### 기업 내부 (C)

| # | 페인포인트 | 내용 |
|---|---|---|
| C1 | 인력 대비 채널 과다 | 해외 담당자 1명이 여러 채널 동시 운영 |
| C2 | 핵심 무기가 해외에서 막힘 | 국내 성공 공식 "숙취해소력 중심" 메시지를 미국에서 사용 불가 |
| C3 | 국내 콘텐츠 재활용 불가 | 한국 규제·음주 문화 기준 콘텐츠는 번역만으로 못 씀 |
| C4 | 단일 제품 의존 | 매출 90%+가 알디콤 한 라인업 |
| C5 | 미국 내 브랜드 인지도 부족 | 설립 2년 차, 미국은 아시아계 채널 위주 |
| C6 | 성장 목표 vs 리소스 | 2030년 연매출 1,000억원 목표, 현지 대행사 없음 |

### 미국 시장 (M)

| # | 페인포인트 | 내용 |
|---|---|---|
| **M1** ⭐ | FDA 질병 주장 규제 | FDA는 숙취를 '알코올 중독' 증상으로 봄 → 숙취 효능 주장 = 질병 치료·예방 주장. 2020.07 7개사 경고장 (예: *"Helps prevent hangover symptoms"*) |
| M2 | 규제 위반이 흔한 시장 | 미국 숙취 제품의 41.3%가 불법 질병 주장 → 경쟁사 표현 모방 위험 |
| M3 | 인플루언서 발언도 브랜드 책임 | FTC 보증 가이드상 크리에이터의 건강 주장도 브랜드 책임 |
| M4 | 카테고리 인식 차이 | 미국은 전해질 제품이 39.9%로 최대 → "숙취 관리 = 수분 보충" 인식 |
| M5 | 효능에 대한 소비자 불신 | 제품 효능 회의론 |
| M6 | 채널 분절 | Amazon(영어 SEO) / Weee·Yamibuy(이중언어) / SNS(숏폼) 고객·형식·톤 상이 |
| M7 | 음주 시즌성과 시차 | 금·토 밤, 핼러윈·추수감사절 전날·새해 집중. 미국 피크 = 한국 밤·주말 |
| M8 | 광고 플랫폼 정책 | 21세 이상 타겟팅, 과음 조장 금지 등 (확인 필요) |

> **결론:** 서연의 고통은 **"규제 확인"**과 **"채널별 재작성"** 두 가지 반복 업무에 몰려 있다.

## 4. 서비스 설계 원칙

| # | 원칙 | 구현 기준 |
|---|---|---|
| 01 | **입력은 한국어, 출력은 미국용** | 모든 AI 입력창은 한국어 입력을 기본으로 함 |
| 02 | **판정에는 반드시 FDA 사례 근거** | 심의 결과에 근거 경고장·문구 링크 필수 표시 |
| 03 | **검증 → 현지화가 하나의 흐름** | 위험 표현 지적 시 대안 카피를 함께 제시, 바로 채널 카피 생성으로 연결 |
| 04 | **채널별 카드 + 원클릭 복사** | 3개 채널 결과를 한 화면에서 비교, 카드마다 복사 버튼 |

**❌ 만들지 않을 것**
- 영어로 긴 프롬프트를 써야 하는 UI
- 근거 없이 "위험합니다"만 말하는 판정
- 지적만 하고 끝나는 검사기
- 채널마다 메뉴를 왔다 갔다 해야 하는 구조
- 세팅이 복잡한 대시보드, 다시 손봐야 하는 초안

**⏱️ 목표:** 카피 1건 기준 **입력 → 심의 → 채널별 카피 복사까지 10분 이내**

## 5. 메뉴 구성

### 데이터 유형 범례

| 표기 | 의미 |
|---|---|
| `API` | 외부 API 실시간/주기 호출 |
| `수동` | 팀이 수집·작성한 CSV/JSON 파일 업로드 |
| `크롤링` | 공개 웹페이지 수집 (robots.txt 확인) |
| `AI` | LLM 생성·요약·판정 |
| `입력` | 사용자가 화면에서 직접 입력 |
| `자동` | 시스템 내부 로직 (저장·분기·패키징) |
| `더미` | 시연용 가상 데이터 |

### 우선순위

- **P0** — 핵심 기능, 반드시 먼저 완성 (서연의 1·2순위 페인포인트)
- **P1** — 주요 기능
- **P2** — 추가 기능

### 전체 메뉴 트리

```
REBOOT US 마케팅 대시보드
│
├── [상단 탭] ─ 화면 왼쪽부터 이 순서로 표시
│   ├── 🏠 홈 · 데일리 브리핑 ............ P1
│   ├── 🔍 시장 · 고객 인사이트 .......... P1
│   ├── ✍️ 콘텐츠 제작 ................... P0
│   ├── 🛡️ 컴플라이언스 .................. P0
│   ├── 💬 고객 응대 (CS) ................ P1
│   ├── 🤝 인플루언서 · 파트너 ........... P1
│   └── 📊 성과분석 (비용 대비 매출)
│
└── [탭 아님]
    ├── 🔐 로그인
    └── ⚙️ 설정
```

## 6. 폴더 구조

> 폴더·브랜치·PR 등 협업 규칙은 [`RULE.md`](./RULE.md)를 따릅니다. 이 절은 `RULE.md` §5를 이 프로젝트에 적용한 모습입니다.
> 6명이 동시에 작업하므로 **파트(메뉴)별로 폴더를 완전히 분리**하고, 각자 **자기 파트 폴더 안에서만** 라우트 · 화면 · 로직 · 데이터를 만듭니다.

```
reboot-us-dashboard/
├── app.py                   # create_app() · 모든 파트 Blueprint 등록 (공통)
├── config.py                # 설정값 (공통)
├── requirements.txt         # 패키지 목록 (공통)
├── .env.example             # 환경 변수 예시 (공통, 실제 값 없음)
├── .gitignore / .gitattributes
├── README.md / RULE.md / AI_RULES.md
├── AGENTS.md / CLAUDE.md / GEMINI.md / .geminiignore   # AI 도구 설정 (공통)
│
├── core/                    # 🔒 공통 (팀장·PM과 협의 후 수정)
│   ├── services/
│   │   ├── llm.py           #    AI 호출 공통 함수 (OpenAI API)
│   │   └── db.py            #    DB 연결
│   ├── templates/           #    base.html (레이아웃 · 사이드바)
│   └── static/              #    공통 CSS · JS
│
├── home/                    # 🏠 홈 · 데일리 브리핑 .......... 현경 (HK)
├── insight/                 # 🔍 시장 · 고객 인사이트 ........ 현경 (HK)
├── content/                 # ✍️ 콘텐츠 제작 ................. 나원 (NW)
├── compliance/              # 🛡️ 컴플라이언스 ................ 준희 (JH)
├── cs/                      # 💬 고객 응대 (CS) .............. 준희 (JH)
├── influencer/              # 🤝 인플루언서 · 파트너 ......... 혁주 (HJ)
├── performance/             # 📊 성과분석 .................... 혁주 (HJ)
├── auth/                    # 🔐 로그인 (탭 아님) ............ 현경 (HK)

│
├── tests/                   # 파트별 하위 폴더로 분리 (tests/home/, tests/cs/ ...)
└── instance/                # 로컬 DB 등 (Git에 올리지 않음)
```

### 파트 폴더 내부 구성 (공통 규칙)

모든 파트 폴더는 같은 모양으로 만듭니다. (예: `content/`)

```
content/
├── __init__.py      # Blueprint 정의 (url_prefix="/content")
├── routes.py        # URL · 화면 연결
├── services/        # 이 파트의 로직 · 외부 API 호출
├── models.py        # 이 파트에서만 쓰는 DB 테이블
├── prompts/         # 이 파트의 AI 프롬프트
├── templates/
│   └── content/     # 화면 HTML (파트 이름 폴더로 한 번 더 감싸 이름 충돌 방지)
├── static/
│   └── content/     # 이 파트 전용 CSS · JS · 이미지 (템플릿과 같은 이유로 감쌈)
├── data/            # 이 파트의 수동 · 더미 데이터
└── README.md        # 파트 README (담당자 작성, RULE.md §5.4)
```

### 충돌 방지 규칙

| 규칙 | 내용 |
|---|---|
| 내 폴더만 수정 | 자기 파트 폴더 밖의 파일은 수정하지 않습니다. 다른 사람의 코드는 작성자와 먼저 협의합니다. |
| 공통 영역은 협의 후 | `app.py`, `config.py`, `requirements.txt`, `.env.example`, `core/` 등(`RULE.md` §5.2)은 팀장 또는 PM과 협의한 뒤 PR로 수정하고, PR에 공통 영역 수정임을 표시합니다. |
| URL 접두사 고정 | 파트마다 `/home`, `/insight`, `/content`, `/compliance`, `/cs`, `/influencer`, `/performance`, `/auth`, `/settings`를 사용합니다. |
| DB 테이블 이름 | 파트 이름을 앞에 붙입니다. (예: `cs_inquiry`, `content_campaign`) |
| 다른 파트 기능 사용 | 다른 파트의 코드는 **가져다 쓰기만** 하고 수정하지 않습니다. 먼저 그 파트 README의 "다른 파트에 제공하는 함수"를 확인합니다. (예: CS · 콘텐츠 · 인플루언서 → `compliance.services`의 심의 함수 호출) |
| 브랜치 | `main`·`pre_main`에 직접 push하지 않습니다. 최신 `pre_main`에서 기능마다 `feature/이니셜-기능명` 브랜치를 새로 만들고 `pre_main`으로 PR합니다. (`RULE.md` §3·§4) |
| 패키지 추가 | 패키지가 필요한 PR에서 `requirements.txt`에 버전을 고정해 직접 추가하고, PR에 이유를 적습니다. `pip freeze`로 파일 전체를 덮어쓰지 않습니다. (`RULE.md` §8.2) |
| 두 파트 담당 | 두 파트를 맡은 사람도 파트마다 브랜치 · PR을 따로 만듭니다. (예: 준희 — `compliance/`와 `cs/` 변경을 한 PR에 섞지 않음) |

## 7. 설치 및 실행

명령은 Windows `cmd` 기준입니다. (`RULE.md` §8.1)

1. 저장소를 받고 가상환경을 만듭니다.

```cmd
git clone <repository-url>
cd reboot-us-dashboard
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```

2. 환경 변수 파일을 만들고, `.env`에 각자 받은 API 키를 채웁니다.

```cmd
copy .env.example .env
```

3. DB를 초기화하고 더미 데이터를 넣은 뒤 개발 서버를 실행합니다.

```cmd
flask init-db
flask seed-dummy
flask run --debug
```

브라우저에서 `http://127.0.0.1:5000` 접속

> 처음 받은 뒤 `main`·`pre_main` push 차단 훅을 각자 설치합니다. (`RULE.md` §10.1)

## 9. 배포

```bash
# 프로덕션 실행
gunicorn -w 2 -b 0.0.0.0:8000 "app:create_app()"
```

**배포 체크리스트**

- [ ] `SECRET_KEY` 운영용 값으로 교체
- [ ] `DEBUG` 비활성화 (`FLASK_DEBUG` 미설정 또는 `0`)
- [ ] 운영 DB 설정 (`DATABASE_URL`)
- [ ] 모든 API 키를 배포 플랫폼 환경 변수로 등록
- [ ] Gmail OAuth Redirect URI를 배포 도메인으로 등록
- [ ] SerpApi · YouTube 쿼터 초과 시 fallback 동작 확인
- [ ] 로그인 없이 내부 페이지 접근 불가 확인

### Render 배포 설정

| 항목 | 값 |
|---|---|
| Service Type | Web Service |
| Runtime | Python 3 |
| Build Command | `pip install -r requirements.txt` |
| Start Command | `gunicorn -w 2 -b 0.0.0.0:$PORT "app:create_app()"` |
| Environment | §8의 환경 변수를 Render 대시보드 → Environment에 등록 |

> ⚠️ **SQLite 사용 시 주의:** Render 기본 파일시스템은 재배포 · 재시작 때 초기화됩니다.
> 심의 이력 · 협업 이력 · 작업 로그를 유지하려면 **Persistent Disk**를 붙이고 DB 경로를 디스크로 지정하세요.
> (예: 디스크 마운트 `/var/data` → `DATABASE_URL=sqlite:////var/data/reboot.db`)
> Persistent Disk는 유료 플랜에서 제공되므로, 무료 플랜이면 시연 전 `seed-dummy`로 데이터를 다시 적재하는 방식으로 운영합니다.
